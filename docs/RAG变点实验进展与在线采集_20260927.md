## 检测器试跑的解释

将同一批 40 题重排 200 次，在第 20 题之后切换为故障答案。拒答代理是检测器唯一输入；金标准、F1、LLM 评分都不进入检测器。原始逐题输入下，200 种顺序均在变点后报警，报警时平均延迟 4.5 个查询。

这些顺序重复使用同一批答案，不能当成独立线上试验。用于估计正常均值上界的 126 条旧答案也不具备已验证的逐时条件均值性质。因此目前不能报告真实 1% 误报率或理论保证。重叠窗口的条件均值问题仍然存在。

## 真实请求的后续采集

`rag_server.py` 的 HTTP `/ask` 与 MCP `ask`（DeepSeek Harness 使用的入口）现在为每次请求在 JSONL 中记录：时间、请求 ID、通道、语料、问题哈希、问题和答案长度、显式拒答、是否无检索证据、生成是否成功。日志不写问题或答案原文。

`export_online_quality.py` 按时间导出成功问答。现有 `data/observability.jsonl` 只有 5 条旧 ask 事件，均没有新代理；新代码需要在服务下次启动后才会记录。采集期须保持正常配置，并把脚本测试或故障演练与真实使用时段分开。MCP 通道标签本身不能证明请求是独立真实用户流量。

28 条新题仍为 `pending`。在加入正式评测前，需要独立核对问题、答案和 PDF 原件，优先处理 8 条黄色题。
